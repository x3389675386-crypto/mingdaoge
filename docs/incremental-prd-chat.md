# 明道阁私聊系统 · 增量 PRD（产品需求文档）

> 文档状态：增量需求（在已有项目上开发）
> 作者：产品经理 许清楚（Xu）
> 适用范围：游客私聊系统（用户↔用户、用户↔客服）
> 关联架构设计：见第 6 节「待确认问题 / 技术权衡」，转交架构师决策

---

## 0. 重要边界声明（全员必读）

- **不引入登录系统。** 不做注册、登录、密码、第三方 OAuth、也不使用 Supabase 匿名登录（Anon Auth）。
- **游客身份 = 前端 localStorage 持久化的 `guest_id` + 昵称。** 换设备 / 清缓存即视为新游客，历史会话不可见，此限制用户已知晓并接受。
- 本 PRD 只做产品分析，不含实现代码。

---

## 1. 产品目标（一句话）

在不引入任何登录体系的前提下，让游客以「填昵称」的轻量方式，与商家客服及其他游客之间建立准实时的私信沟通，提升咨询转化与社区互动。

---

## 2. 用户故事

1. **作为游客，我希望**首次进入私聊时填一个昵称并被记住，**以便**无需注册也能发起和接收私信。
2. **作为游客，我希望**在论坛帖子/晒图下方点「私聊」直接给对方发消息，**以便**就同好话题私下交流（用户↔用户）。
3. **作为游客，我希望**在任意页面点「联系客服」给明道阁发私信，**以便**咨询商品/订单而不公开留言。
4. **作为商家（客服），我希望**在 `/admin` 后台看到用户发来的私信并回复，**以便**及时处理咨询。
5. **作为游客，我希望**之后能修改自己的昵称，**以便**更正或保护隐私。

---

## 3. 需求池（按优先级）

> 优先级：P0 = 必须随首版上线；P1 = 首版后尽快补；P2 = 增强体验，排期视资源。
> 每条含：编号 / 功能 / 说明 / 验收标准（AC）。

### P0 核心

**P0-1 游客昵称设置（首次）**
- 说明：首次触发任意私聊功能时，弹窗要求填写昵称（≤20 字，复用论坛文明词过滤 `containsProfanity`）。前端生成随机 `guest_id`（如 `crypto.randomUUID()`），与昵称一并发 `localStorage`（key 建议 `mingdao_guest`，结构 `{guest_id, nickname}`）。已存在则不再弹窗。
- AC：
  1. 清空 localStorage 后首次进入私聊弹窗出现，可输入并保存；
  2. 刷新页面昵称与 id 保持，不再弹窗；
  3. 昵称含违规词被拦截并提示（复用现有过滤逻辑）。

**P0-2 会话列表（我参与的会话）**
- 说明：展示当前 `guest_id` 参与的会话（仅应用层过滤，见第 6 节 RLS 权衡）。每条显示对方昵称、最后一条消息预览、时间、未读角标。
- AC：
  1. 列表只显示当前游客作为 sender 或 receiver 的会话；
  2. 新消息到达（含 Realtime）列表实时刷新并置顶；
  3. 空态有引导文案（见 P2-2）。

**P0-3 私聊对话窗口**
- 说明：进入某会话展示消息流（左右气泡区分自己/对方）、时间、输入框。底部支持文本发送；图片发送见 P2-1。
- AC：
  1. 自己消息靠右、对方靠左，昵称/时间可见；
  2. 进入会话自动拉取历史（按 `created_at` 升序）；
  3. 发送后本地即时上屏，无需等待回包。

**P0-4 发消息 + Realtime 实时接收**
- 说明：发送写 `chat_messages` 表；前端用 Supabase Realtime 订阅该表 `INSERT`（按当前 `guest_id` 过滤 sender/receiver），延迟目标 <1s。未配置 Supabase 时降级为本地 state（不实时，仅自娱）。
- AC：
  1. 对方发来的消息在 <1s 内出现在当前会话；
  2. 未配置 Supabase 时不报错，消息仅本机可见；
  3. 断线重连后补拉遗漏消息（订阅 `postgres_changes` + 进入会话时 `select`）。

**P0-5 用户↔用户 私聊**
- 说明：任意两个游客凭对方 `guest_id` 互发。发起入口见 P2-3（首版可先用「输入对方昵称/从会话新建」兜底，P0 不强制入口）。
- AC：
  1. 已知对方 `guest_id` 可创建会话并发消息；
  2. 双方都能收到并实时查看。

**P0-6 用户↔客服 私聊**
- 说明：用户给固定客服身份发消息。客服固定身份建议 `guest_id = "admin"`，昵称「明道阁客服」（具体定值见第 6 节待确认）。前台提供「联系客服」入口（导航栏 + 商品页 + 页脚）。
- AC：
  1. 点「联系客服」打开与 `admin` 的会话；
  2. 用户消息写入 `chat_messages` 且 `receiver_id = "admin"`；
  3. 商家后台可回复（见 P0-7）。

**P0-7 后台客服回复入口**
- 说明：在 `/admin` 新增「客服私信」Tab（复用现有 `AdminRoute` 密码鉴权）。展示会话列表 + 对话窗口，商家以 `admin` 身份回复。
- AC：
  1. 后台能看到所有发给 `admin` 的会话与消息；
  2. 商家回复实时写入并推送给用户；
  3. 支持未读标记（接 P1-1）。

### P1 增强

**P1-1 未读消息数提示**
- 说明：导航栏私聊入口显示未读总数角标（复用 `Badge` 组件，类比购物车/留言）。
- AC：收到新消息且会话非当前打开时角标 +1；进入会话清零。

**P1-2 消息已读标记**
- 说明：`chat_messages.is_read` 字段；接收方进入会话或收到消息后上报已读。
- AC：发送方消息在对方已读后显示「已读」状态；后台可见用户消息是否已读。

**P1-3 游客可修改昵称**
- 说明：设置页/私聊入口下拉提供「修改昵称」，更新 `localStorage` 昵称；新发消息用新昵称（旧消息昵称冗余存储不变）。
- AC：修改后新消息显示新昵称，旧消息不受影响；`guest_id` 不变。

### P2 体验增强

**P2-1 表情 / 图片消息**
- 说明：文本支持表情（复用论坛 `QUICK_EMOJIS` 快捷面板）；图片复用现有 Supabase Storage `images` 桶上传 + base64 兜底，`chat_messages.type='image'` + `image_url`。
- AC：可发图并在气泡内渲染；未配置 Supabase 时图片仅本机可见。

**P2-2 空状态引导**
- 说明：无会话时展示引导（如「还没私信？去论坛找同好，或联系客服」）。
- AC：空态有文案与跳转入口。

**P2-3 防骚扰 / 用户间发起入口**
- 说明：用户间需先获得对方 `guest_id` 才能发起。在论坛帖、晒图、评论处加「私聊」按钮（携带对方 `guest_id`）。**前提（本次不实现）**：论坛帖/评论/晒图需新增 `guest_id` 字段并落库（当前仅存昵称，无 id），该库表改造已推迟至独立排期，不阻塞首版。首版 P0 以「手动输入对方昵称/guest_id 新建会话」兜底。
- AC：点帖子作者「私聊」直接打开与其 `guest_id` 的会话；无 `guest_id` 的内容不显示该按钮。

## 4. UI / 交互要点

- **昵称设置弹窗**：MUI `Dialog`，标题「设置昵称」，单 `TextField`（placeholder「匿名道友」），底部「确定」。复用论坛文明词过滤。
- **会话列表页**（`/chat` 路由或抽屉）：左侧会话列表（对方昵称 + 最后消息 + 时间 + 未读角标），点击进入右侧对话窗口（移动端全屏切换）。顶部返回/新建。
- **私聊窗口布局**：顶部对方昵称 + 在线/返回；中部消息气泡流（自己右、对方左，金/红主色系，沿用 `#c9a96e`）；底部输入框 + 发送按钮（+ 图/表情入口 P2）。
- **后台客服 Tab**：复用 `AdminPanel` 的 `Tabs` + `TabPanel`。列表展示用户昵称/最后消息/未读；右侧商家回复框，以「明道阁客服」身份发送。未读角标挂在 Tab 标签上（类比现有「客户留言」Tab）。
- **导航入口**：`Navbar` 的 `navLinks` 增加「私聊」（路由 `/chat`），桌面与移动抽屉同步；角标显示未读（P1-1）。「联系客服」作为快捷按钮置于导航右侧/页脚。

## 5. 数据模型建议（草案，最终由架构师定稿）

- `chat_messages`：`id` (bigint PK)、`sender_id` (text)、`sender_name` (text)、`receiver_id` (text)、`receiver_name` (text)、`content` (text)、`type` ('text'|'image')、`image_url` (text?)、`is_read` (bool)、`created_at` (timestamptz)。
- 可选 `conversations` 表（`id`、`participant_a`、`participant_b`、`last_message`、`updated_at`）以优化会话列表；若架构师认为可从 `chat_messages` 派生则省略。
- 昵称冗余存储于每行，便于显示，修改昵称不影响历史。
- **论坛/晒图/评论需新增 `guest_id` 字段**（P2-3 前置），否则用户间无法关联私聊。

## 6. 待确认问题清单 / 技术权衡（转交架构师）

### 6.1 【关键】RLS 策略权衡（无 Auth 身份）
游客无 Supabase Auth，现有表（`forum_posts` 等）已用 anon key 直写，说明 RLS 当前为开放/宽松。私聊表两种方案：

- **方案 A（推荐，应用层管控）**：`chat_messages` 的 RLS 设为 `USING (true)`（开放读写），但**应用层只 `select` 当前 `guest_id` 作为 sender 或 receiver 的行**，绝不暴露他人会话。优点：实现简单、兼容现有降级逻辑；风险：数据库层无强制隔离，依赖前端过滤，需架构师评估数据泄露面。
- **方案 B（轻量服务端校验）**：利用 Supabase 的 `requesting_user`/自定义 JWT claim 或数据库函数（RPC）做 `sender_id`/`receiver_id` 校验，RLS 只允许读写「与自己相关」的行。优点：数据库层隔离更严；缺点：需额外 RPC/策略，复杂度高。
- **决策点**：由架构师在「实现成本 vs 安全隔离」间定方案；若选 A，须明确告知用户数据非强隔离。

### 6.2 客服固定身份如何设定
建议 `guest_id = "admin"`、昵称「明道阁客服」。需确认：是否用保留字常量、是否与现有 `messages`（联系留言）表共用、后台回复是否需要区分「系统客服」与「真实店主」。

### 6.3 用户间私聊发起入口【已拍板：方案 B】
**决策（产品经理 Xu，2026-07-20）**：P2-3 的 `forum_posts` / `forum_comments` / `reviews` 三表新增 `guest_id` 字段迁移 **不纳入本次增量范围**，推迟到单独排期（对应架构师 CHAT-12，独立库表改造任务，不阻塞首版）。
- 首版（P0）用户↔用户私聊采用「手动输入对方昵称/guest_id 新建会话」兜底，P0 不带论坛/晒图入口按钮。
- 三表加 `guest_id` 属库表改造（涉及既有数据回填），成本高、影响面大，与「轻量首版」目标不符，故定为后续独立任务。
- P0-6「联系客服」为固定客服身份，与「客户留言」表语义不同，确认为独立客服私信 Tab，不复用留言表（与架构师设计一致）。

### 6.4 Realtime 订阅范围
订阅整表 `INSERT` 后前端按 `guest_id` 过滤，还是使用 Realtime 的过滤参数？需架构师按方案 A/B 选择，确保 <1s 延迟与断线补拉。

### 6.5 未配置 Supabase 的降级行为
私聊在 `isSupabaseConfigured=false` 时是否完全隐藏入口，还是仅本地自娱？建议：保留入口但提示「未连接云端，消息仅本机」，由产品/架构确认。

### 6.6 昵称唯一性与冲突
`guest_id` 随机保证唯一；昵称可重名，UI 用 `guest_id` 区分会话，是否需要展示「昵称#后缀」防混淆？待定。

---

## 7. 验收总览（非功能）

- 实时性：消息端到端可见延迟 < 1s（同网络）。
- 兼容性：未配置 Supabase 时不崩溃，私聊降级为本地。
- 性能：会话列表 / 消息流分页或限量（如最近 200 条），避免长列表卡顿。
- 安全：即便采用 RLS 方案 A，应用层严格过滤，不展示非本人会话。
